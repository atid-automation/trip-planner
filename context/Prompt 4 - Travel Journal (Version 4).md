# Prompt 4 — Travel Journal (Version 4)

You are continuing development of the existing **Trip Planner web application**.

This is **Version 4** of the application.

Version 1 introduced trip and itinerary management.

Version 2 introduced user registration, authentication, authorization, and trip ownership.

Version 3 introduced trip budgets and expense management.

Now we are adding a **Travel Journal** feature.

---

# 1. Critical Rule — Preserve Existing Functionality

**Do NOT rewrite the application from scratch.**

**Do NOT remove or redesign existing functionality unless required to support the Travel Journal.**

All existing functionality must continue to work:

- User registration
- Login
- Logout
- Authentication
- Authorization
- Trip management
- Itinerary management
- Budget management
- Expense management
- JSON persistence
- Existing REST API

The goal is to extend the existing application.

Do not refactor unrelated parts of the application.

---

# 2. New Feature — Travel Journal

Users should be able to keep a personal journal for each trip.

A journal consists of multiple entries associated with a specific trip.

For example:

```text
Trip: Vietnam Adventure

Journal

October 1
"Arrived in Hanoi today. The city is much more chaotic than I expected..."

October 3
"Spent the entire day exploring the Old Quarter..."

October 5
"Tomorrow we're heading to Ha Long Bay."
```

The journal is intended to represent a simple personal travel diary.

Keep the feature intentionally small.

---

# 3. Journal Entry Data Model

Create a Journal Entry entity.

A possible structure:

```text id="7d9nps"
JournalEntry
- id
- trip_id
- title
- content
- date
- created_at
- updated_at
```

You may adjust the exact implementation if necessary, but keep the model simple.

Each journal entry must belong to exactly one trip.

Do not create unnecessary entities.

---

# 4. Journal Entry Management

The user must be able to:

1. View journal entries for a trip
2. Create a journal entry
3. View a single journal entry
4. Edit a journal entry
5. Delete a journal entry

Display journal entries in chronological order, with the newest entry first.

---

# 5. Journal Entry Fields

A journal entry contains:

### Title

Required.

Maximum length: 100 characters.

### Content

Required.

Maximum length: 5,000 characters.

### Date

Required.

Must be a valid date.

The date should normally fall within the trip's date range.

Use the same date-related principles already used elsewhere in the application.

### Timestamps

The system should automatically maintain:

- `created_at`
- `updated_at`

These timestamps must be generated by the backend.

Do not allow the client to arbitrarily set these values.

---

# 6. Validation

Implement validation on both frontend and backend.

Rules:

- Title is required.
- Title must not exceed 100 characters.
- Content is required.
- Content must not exceed 5,000 characters.
- Date is required.
- Date must be valid.
- Journal entry date should fall within the trip date range.

Provide clear and deterministic validation messages.

Do not implement overly complicated validation.

---

# 7. REST API

Add REST endpoints similar to:

```text id="c7ny4p"
GET    /api/trips/{trip_id}/journal
POST   /api/trips/{trip_id}/journal

GET    /api/trips/{trip_id}/journal/{entry_id}
PUT    /api/trips/{trip_id}/journal/{entry_id}
DELETE /api/trips/{trip_id}/journal/{entry_id}
```

All endpoints must require authentication.

All endpoints must enforce the authorization model from Version 2.

A user must only be able to access journal entries belonging to their own trips.

Do not trust a client-provided `user_id`.

The server must determine ownership through the authenticated user and the trip relationship.

---

# 8. Authorization Requirements

The following must be enforced server-side:

User A must not be able to:

- View User B's journal
- Create a journal entry in User B's trip
- View User B's journal entry
- Modify User B's journal entry
- Delete User B's journal entry

Do not rely on hiding UI elements.

The API itself must reject unauthorized requests.

# 10. Long Text Handling

The content field may contain multiple paragraphs.

Preserve line breaks when displaying journal content.

Do not interpret journal content as HTML.

Treat the content as plain text.

This is important for both security and predictable rendering.

Do not add a rich-text editor.

Do not support Markdown in this version.

# 15. Important Business Rules

The implementation must correctly handle:

1. Empty title
2. Empty content
3. Title longer than 100 characters
4. Content longer than 5,000 characters
5. Invalid date
6. Journal date outside the trip date range
7. Editing an existing entry
8. Deleting an entry
9. Multiple entries for the same date
10. Chronological ordering
11. Unauthorized access to another user's journal
12. Multiline journal content

Do not introduce additional complex business rules.

---

# 16. Interaction With Existing Features

Journal entries belong to trips.

Therefore:

- Deleting a trip must not leave orphan journal entries.
- Editing a trip's dates must be handled consistently with existing journal entries.
- If the application prevents a trip date change that would invalidate existing journal entries, implement this explicitly and document it.
- If the application allows the change, ensure the journal remains consistent.

Choose the simplest predictable behavior.

Do not introduce complicated cascading systems.
